# Choose Dispositions for Foreground Engine and Analysis Capabilities

Type: grilling
Status: resolved
Blocked by: 01, 04

## Question

Given the cross-cutting Entry Point census, [Inventory Foreground Engine and Analysis Capabilities](04-inventory-engine-analysis.md), and the standing R3 decisions, which engine and analysis behaviors are equivalent migrations, Next redesigns, deferred, abandoned, or implementation-only; how should oversized ENG/ANA claims split into stable Parity Items; and which defaults, persistence, identity, cancellation, failure/recovery, evidence, and acceptance contracts belong in R3 versus later dependent phases?

## Answer

### Frozen claim boundary

Accepted `ENG-01`, `ANA-05`, `UI-03`, and `UI-04` keep their original scope, status, and evidence. This decision does not add engine lifecycle, Java profile fields, tracking analysis, Java in-tree cache behavior, SGF analysis exchange, or additional presentation preferences to those claims. Existing Missing and Partial items may be split below because their outstanding contracts are not accepted history.

### Canonical model

- An **Engine Adapter** translates manager lifecycle, game-play, and analysis operations to one protocol and declares the capabilities that protocol and run actually provide.
- An **Engine Profile** is durable adapter-specific launch configuration with a stable identity. Shared fields are name, program, argument vector, and working directory; the adapter owns additional assets and settings. Existing `ENG-01` acceptance remains limited to its KataGo analysis fields, while `ENG-09` owns the multi-backend successor.
- The **Autoload Default** is the zero-or-one Engine Profile marked for startup. No marked profile means autoload is off. It is distinct from the profile selected for editing in Engine Settings and from the profile snapshot owned by the current run.
- A **Foreground Engine Run** is one manager-owned resident process created from an immutable Engine Profile and capability snapshot. One run speaks one adapter protocol. Editing its source profile produces pending changes; only explicit Restart creates a run from the new profile.
- An **Analysis Job** has manager-owned run, job, and node/game scope and requires the corresponding run capability. Jobs occupy either the selected-node lane or the whole-game lane. Supersession is lane-local; Stop, Restart, switch, crash, and application exit cancel every job owned by the affected run.
- Engine Settings edits the catalog and Autoload Default without starting or switching a run. The main-workspace Engine Switcher starts or switches the Foreground Engine Run. Unsupported actions are disabled or rejected before process or current-game mutation.

### Stable Parity Item boundaries

- `ENG-02` — **Foreground Engine Run**: one manager owns the no-engine/starting/ready/stopping/error state and an immutable adapter/profile/capability snapshot. Start validates assets and adapter readiness before publishing the run. Dedicated Stop cancels every run-owned job and terminates the process. Explicit Restart cancels every old-run job, terminates that process, and replaces it from current saved profile data; it never changes protocol in place. Settings selection and edits never start, switch, or mutate a run.
- `ENG-03` — **Transactional Foreground Switch**: start B while A remains primary; promote only a ready B for the current switch identity; cancel A jobs, route new jobs to B, then stop A. The active profile cannot be deleted; another profile can become primary only through this transaction.
- `ENG-04` — **Failed Switch and Stale Identity Rejection**: failed B leaves A ready and primary; a superseded switch or late process/job event cannot alter current identity, status, or presentation. If A no longer exists, failure yields the explicit no-engine state rather than promoting B.
- `ENG-05` — **Cancellable Selected-node Job Identity**: the manager owns selected-node job start, explicit cancellation, completion, and supersession. Only the latest job for the current run and node may publish. Query/result correctness remains `ANA-01`; this item owns lifecycle identity.
- `ENG-06` — **Default Foreground Autoload**: the profile catalog persists zero or one Autoload Default, with none as the first-use/off default. Startup with a mark validates and starts that profile; failure reports a typed error and leaves no engine without falling back to another profile. Changing the mark does not change the current run. Deleting an inactive marked profile clears the mark; the active-profile deletion guard still applies. Persistence failure preserves the prior durable mark and reports the failure.
- `ENG-07` — **Foreground Failure and Manual Recovery**: start, asset, protocol, nonzero-exit, timeout, and cancellation outcomes are typed and scoped to the current run. Unexpected exit cancels its jobs and stays in error until explicit Restart. No automatic restart or stale event can replace the current run; profile correction occurs through Engine Settings.
- `ENG-08` — **Engine Profile Catalog Ordering**: stay Deferred. Acceptance requires user-directed first/up/down/last reordering to persist stable profile identities without changing Engine Settings selection, Autoload Default, active run, pending edits, or job binding. Rejected or failed persistence leaves the durable order unchanged.
- `ENG-09` — **Multi-backend Engine Profiles and Capabilities**: extend the accepted KataGo-only `ENG-01` boundary without changing its history. One catalog persists stable profile identity, adapter kind, shared executable/argument/working-directory fields, and adapter-owned settings. Save validates the adapter contract atomically. A run snapshots verified capabilities; profile edits remain pending until Restart or switch. Unsupported actions are rejected before process or current-game mutation.
- `ENG-10` — **Generic GTP Game Adapter**: start a profile, complete a bounded protocol/name/version/list-commands handshake, publish only verified game-play and clock capabilities, synchronize an exactly admissible position, map per-move Compute Budgets, and expose typed command, parse, timeout, exit, and unsupported-capability outcomes. Cancellation and stale run/job/game identities cannot publish a move. Rich-analysis extensions are not part of this item.
- `ANA-01` — **One-shot Position Analysis**: submit the selected position through the manager-owned selected-node lane only after adapter capability and exact-position admission, then expose result, typed failure, explicit cancellation, and supersession. Publication requires current run, job, document generation, and exact `NodePath`.
- `ANA-02` — **Mainline Whole-game Analysis**: one single-stage capability-admitted session analyzes the current game's main line, reports current/completed/remaining progress and node-linked results, supports explicit cancellation, and does not block review navigation. No two-stage, pause/resume, hidden dedicated engine, or lease-wait behavior belongs to this item.
- `ANA-03` — **Analysis Job Lanes**: selected-node and whole-game jobs have independent manager-owned identities and cancellation. Supersession affects only the selected-node lane. Stop, Restart, switch, crash, and exit cancel both lanes for that run, and late events are non-publishing.
- `ANA-04` — **Next-native Analysis Presentation**: candidates, PV mini-board, ownership, policy, and candidate limit render only when the current adapter capability and run/job/node scope are valid. Existing hover and accepted UI behavior retain their original evidence; Java granular review preferences are not successors.
- `ANA-05` — **Analysis Cache Basics**: remains frozen Accepted. Variation-aware changes, Java in-tree cache semantics, and SGF exchange cannot be claimed through this item.
- `ANA-06` — **Continuous Current-node Analysis**: stay Deferred. Acceptance requires an explicit default-off, run-scoped workspace toggle; opening it submits selected-node work, navigation supersedes the prior request, and closing it cancels the lane. Stop, restart, switch, crash, and application exit cancel it and reset the toggle off; no startup or ready event enables it.
- `ANA-07` — **Batch SGF Analysis**: stay Deferred. Acceptance requires a session-only ordered SGF queue, visible per-file pending/running/completed/failed/cancelled state, explicit cancellation, and run/job/file identity that blocks stale publication. Queue state is not persisted or restored, and batch work cannot replace or dirty the current game.
- `ANA-08` — **SGF Analysis Exchange**: stay Deferred. Acceptance requires fixtures for frozen Java analysis-header import, structured candidates/PV/ownership where present, incomplete-placeholder rejection, Next export/reopen, preservation of personal comments and unrelated properties, and no false claim that SQLite and SGF stay synchronized.
- `ANA-09` — **Named Rich-analysis Engine Adapters**: stay Deferred. Each admitted engine/version requires a controlled protocol fixture mapping its candidates, winrate/PV, ownership, streaming, selected-node, and whole-game fields into the Next analysis model. Capabilities are declared independently; missing fields remain unavailable rather than fabricated.

### Phase, persistence, and evidence boundary

- R3 still owns `ENG-02` through `ENG-07`, but [Ticket 12](12-decide-game-mode-dispositions.md) supersedes their KataGo-only transport assumption: the manager and run snapshots are adapter-backed, while the R3 acceptance path must at least prove `KataGoAnalysis`. `ENG-09` and `ENG-10` are hard prerequisites for the later GAME phase; Ticket 15 decides whether they extend R3 or form a separate prerequisite phase.
- R4 owns `ANA-01` through `ANA-04` after the R3 manager exists. `ANA-01` and `ANA-02` use independent lanes under `ANA-03`; every action requires adapter capability and exact-position admission, and `ANA-04` consumes only identity-valid results.
- `ENG-08`, `ANA-06` through `ANA-09`, and the Deferred GAME items remain outside R3/R4 unless Ticket 15 schedules them after their named dependencies. The existence of adapter interfaces cannot pull a Deferred named analysis adapter forward.
- The Autoload Default persists with the profile catalog. Foreground Engine Runs, capability snapshots, and Analysis Jobs never persist or recover across application restart. Continuous-analysis toggles and batch queues are session/run state, not preferences. Existing `max_visits`, Next review preferences, and accepted SQLite cache defaults remain unchanged.
- R3 evidence must include focused state-transition coverage for start/Stop/Restart, immutable adapter/profile/capability snapshots, Autoload Default persistence, A to B promotion and rollback, active-profile deletion, typed failure, cancellation, and stale identities. A controlled JSONL fixture must exercise manager-owned selected-node job start, cancellation, supersession, and stale-result rejection. Real KataGo analysis smoke must prove ready, Stop, Restart, and two-profile switch behavior.
- R4 evidence must exercise exact-node one-shot publication, concurrent selected-node/whole-game lanes, lane-local supersession, progress, explicit cancellation, typed failure, presentation scoping, and pre-invocation rejection of unsupported capabilities. `ENG-09`, `ENG-10`, and `ANA-09` require the profile, Generic GTP, non-KataGo native, and named-adapter evidence defined by Ticket 12 when scheduled.

Ticket 12 supersedes this ticket for multi-backend profile, run, capability, and protocol admission. It also solely owns match-session candidate visibility; its role policy does not restore the black/white review preference abandoned here. Every other lifecycle, job, persistence, failure, and analysis disposition above remains authoritative. Ticket 15 owns rebuilding `docs/JAVA_CAPABILITY_INVENTORY.md`, `docs/PARITY_MATRIX.md`, and `docs/MIGRATION_PLAN.md` from the combined decisions. Ticket 16 owns final inventory/matrix/roadmap traceability. Neither decision ticket changes production behavior or those tracked destination documents.
